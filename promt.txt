You are a senior Python backend engineer, browser-automation engineer, and DevOps architect.

Build a complete, production-oriented browser automation project with the following architecture:

GITHUB + RENDER + TEXT CLIENT

IMPORTANT SAFETY AND SCOPE REQUIREMENTS
---------------------------------------
This system is intended ONLY for websites and accounts that the operator owns or is explicitly authorized to test.

Do NOT implement:
- credential stuffing
- brute-force login attempts
- processing a large combo.txt containing username/password pairs
- automatic rotation through credential lists
- CAPTCHA solving intended to bypass anti-bot protections
- Cloudflare bypasses, stealth mechanisms, fingerprint spoofing, or anti-bot evasion
- proxy rotation intended to evade rate limits or security controls

CAPTCHA and anti-bot pages must instead be detected and reported as:
"MANUAL_ACTION_REQUIRED"

The application must pause and allow an authorized human operator to continue manually.

PROJECT ARCHITECTURE
--------------------

1. GitHub repository
2. Render deployment
3. Python backend running on Render
4. Selenium-controlled Chromium/Chrome browser
5. AI-powered webpage element identification
6. Text-based client
7. Browser preview/stream endpoint
8. Secure task/result API

GitHub is connected to Render.

Every push to the configured GitHub branch should trigger a Render deployment.

Create all required files for a clean repository, including:

- .gitignore

Use environment variables for all secrets.

Never hard-code API keys, passwords, tokens, cookies, or credentials.

BACKEND
-------

Use Python.

Prefer FastAPI for the HTTP API.

The backend must provide:

POST /task

Accept a task containing:

- target_url
- username
- password
- natural_language_instruction

Credentials must be handled only in memory whenever possible.

Never write plaintext passwords to logs.

Never return passwords in API responses.

The backend creates an isolated browser session for the task.

Each task receives a unique task_id.

Provide endpoints similar to:

POST /task
GET /task/{task_id}
GET /task/{task_id}/events
GET /task/{task_id}/preview
POST /task/{task_id}/manual-action
POST /task/{task_id}/stop

Return clear task states:

QUEUED
STARTING
RUNNING
WAITING_FOR_MANUAL_ACTION
SUCCESS
FAILURE
STOPPED
TIMEOUT

SELENIUM
--------

Run Chromium/Chrome through Selenium.

Use the normal browser rendering mode required by the Render environment.

Do not implement stealth techniques or mechanisms intended to defeat anti-bot systems.

The browser must:

1. Navigate to the supplied authorized URL.
2. Wait for the page to load.
3. Inspect the DOM.
4. Collect useful element metadata.
5. Ask the configured AI model to identify relevant elements.
6. Fill the username field.
7. Fill the password field.
8. Identify the appropriate login/submit button.
9. Click it.
10. Wait for the result.
11. Determine whether the login appears successful or unsuccessful.
12. Return a structured result.

The automation must use robust Selenium techniques:

- explicit waits
- WebDriverWait
- expected_conditions
- stale-element recovery
- timeout handling
- page-load timeout
- screenshot capture
- browser console/error handling where available

Do not rely exclusively on fixed sleep() calls.

AI ELEMENT IDENTIFICATION
--------------------------

Use an AI provider abstraction.

The preferred provider should be configurable through environment variables.

Support a Groq-compatible provider.

The preferred model should be configurable, for example:

GROQ_MODEL=...

Do not hard-code the model so it can be changed later.

The AI must NOT receive the user's plaintext password unnecessarily.

For element identification, send only the relevant DOM metadata, such as:

- tag name
- id
- name
- type
- placeholder
- aria-label
- visible text
- role
- nearby labels
- CSS selector candidates
- XPath candidates

Do not send password values to the AI element-selection prompt.

The AI should return strict JSON such as:

{
  "username_selector": "...",
  "password_selector": "...",
  "submit_selector": "...",
  "confidence": 0.95,
  "reason": "..."
}

Validate the JSON using Pydantic.

Never execute arbitrary JavaScript returned by the model.

Never allow the model to provide unrestricted shell commands.

BROWSER AGENT
-------------

Implement a controlled browser-agent loop.

The AI may select from a limited set of actions:

- navigate
- click
- type
- wait
- inspect
- screenshot
- finish
- request_manual_action

Validate every action against an allowlist.

The AI must not have unrestricted access to the operating system.

The AI must not execute shell commands.

The browser agent should maintain a compact state representation to avoid sending the entire webpage to the model repeatedly.

AI prompts should instruct the model to:

- use the minimum number of actions
- prefer stable selectors
- avoid destructive actions
- never expose credentials
- stop when authentication succeeds or clearly fails
- request human intervention when anti-bot protection is encountered

CAPTCHA / ANTI-BOT HANDLING
---------------------------

Do NOT automatically bypass CAPTCHA or Cloudflare.

Detect likely CAPTCHA/anti-bot challenges.

When detected:

1. Stop automated interaction.
2. Set task state to WAITING_FOR_MANUAL_ACTION.
3. Notify the client.
4. Keep the browser session alive for a configurable amount of time.
5. Allow the authorized human operator to complete the challenge manually.
6. Resume only after explicit confirmation.

Examples of detected states:

- CAPTCHA
- reCAPTCHA
- hCaptcha
- Cloudflare challenge
- "verify you are human"
- unusual traffic
- access denied
- rate limit

BROWSER PREVIEW
---------------

Implement a browser preview suitable for viewing from an Android device.

The client should display the preview URL returned by the backend.

The preview should provide a near-real-time view of the browser session.

Prefer a standards-based browser-streaming solution that can operate in a Render container.

If direct VLC-compatible streaming is technically unsuitable, document the limitation and implement the most practical HTTP/MJPEG or WebRTC-based preview.

Do not claim that VLC compatibility is guaranteed unless the chosen protocol is actually supported.

The preview must be protected by an authentication/session token.

Do not expose browser sessions publicly without authorization.

CLIENT
------

Create a separate Python command-line client.

The client should:

1. Start.
2. Display the backend connection status.
3. Request or display the browser preview URL.
4. Ask the operator for the target URL.
5. Ask for ONE username.
6. Ask for ONE password securely without echoing it.
7. Send exactly one authorized test task.
8. Wait for the backend result.
9. Display progress.
10. Display SUCCESS, FAILURE, STOPPED, TIMEOUT, or MANUAL_ACTION_REQUIRED.
11. Display the reason/result.
12. Optionally save a screenshot after successful completion.

The client must never print passwords.

Do not implement automatic credential-list processing.

If a local credential file is supported for convenience, it must require explicit operator selection of a SINGLE entry and must never automatically iterate through multiple credentials.
